# Инструкция для специалиста по серверу: переход с v0.8.1 на v0.10

1. Сохранить резервную копию **PostgreSQL** (`pg_dump`), а также текущий `.env`. Проверить доступность архива дампа до переключения.
2. Обновить файлы проекта кодом из этого ZIP, **не заменять текущий `.env`** и не уничтожать постоянный Docker volume PostgreSQL. В ZIP секретов нет.
3. Проверить, что в `.env` задан `SUPER_ADMIN_ID` нужного Telegram-аккаунта, а `DATABASE_URL` указывает на действующую PostgreSQL. Если сервер использует отдельную БД — сохранить прежние учётные данные.
4. Остановить/заменить старую копию бота и **не держать параллельное polling-подключение с тем же токеном**.
5. Из папки с `compose.yaml` выполнить `docker compose up -d --build`. Не использовать `docker compose down -v`.
6. Убедиться в логах `docker compose logs --tail=120 bot`, что бот запущен и планировщик не выдаёт ошибок. Модели `review_deliveries` и другие таблицы создаются `Base.metadata.create_all`; на существующие столбцы миграций нет. Для production в будущем предпочтительны Alembic-миграции.
7. С аккаунта супер-администратора отправить в личный чат Майи `/schedule_status`. Должен отобразиться список из девяти событий с состоянием «ожидает времени» (если они ещё не наступили). Отправить `/menu` и проверить «Путь героя».
8. Проверить регистрацию на лекцию, ответ через Reply из группы поддержки и подключение группы проверки (`UPDATE_TO_V09.md`). Для проверки отправки запланированных сообщений без ожидания даты использовать тестовую БД/бота, а не менять production-календарь.
9. Пожалуйста, отслеживать логи вокруг **22.11 в 14:00 МСК**. Одного факта запуска приложения недостаточно, чтобы гарантировать доставку в Telegram всем пользователям: некоторые могут заблокировать бота.

### Особенности рассылок
- Данные об очереди хранятся в PostgreSQL, переживают перезапуск контейнера.
- Одно событие ставится каждому пользователю в очередь не более одного раза; повторное уведомление после успешной отметки не запланировано.
- Если версия установлена позже чем через 30 минут после назначенного времени, конкретная просроченная рассылка **пропускается** вместо массовой отправки задним числом. Статус `skipped_late` виден в `/schedule_status`.
- Новые пользователи, которые начинают работу после сюжетного дропа, получают пропущенные лорные сообщения после первого `/start`, с паузой в 12 сек. Напоминания о прошедших лекциях не досылаются.

## Как проверить на сервере
```
docker compose ps
docker compose logs --tail=120 bot
```
В Telegram (с аккаунта SUPER_ADMIN_ID):
```
/schedule_status
/menu
/admin
```
